# 14 產品成效與使用數據

**用途**：定義怎麼知道產品有沒有效、要記錄哪些使用行為、在哪裡看，作為之後優化介面與改良功能的依據。

---

## 一、原則

| 原則 | 做法 |
|------|------|
| **跟著產品願景量** | 這個產品刻意「偶爾用也完整」，**不以每日活躍、連續使用天數當目標**。看的是每月有沒有「料理交流」，以月為單位 |
| **記操作，不記內容** | 只記「做了什麼操作」（例如發佈了一篇食譜、有幾張照片），**不記任何內容**（食譜文字、照片、食材名稱、留言都不記） |
| **只在自己的資料庫** | 不用第三方分析工具；事件存在 Supabase，不送到其他服務 |
| **只看匯總，不看個人** | 後台只顯示匯總數字；人數少於 5 人的分組不顯示，避免從數字反推出是誰；沒有「某個人做了什麼」的查詢（延續「看得到營運，看不到別人的生活」） |
| **使用者可以不參與** | 設定裡有「不參與使用統計」；關閉後不記錄事件，也不納入任何產品數據 |
| **小樣本先看質性** | 初期只有 30 位親友，數字波動大。數字用來看趨勢、找問題，原因靠訪談與回饋確認 |

---

## 二、要看的指標

### 主指標：每月有「料理交流」的人數比例

**當月至少做過一件事**的使用者，佔當月有打開 App 的使用者比例：

- 記錄一道菜（發佈食譜，或「又做了一次」）
- 收藏朋友的食譜或大廚的點子
- 對朋友的食譜按反應或留言

它同時反映社群核心（朋友之間的互動）和記錄的價值；只是打開看看、沒有任何交流，不算在內。

### 輔助指標

| 面向 | 指標 | 回答的問題 | 資料來源 |
|------|------|-----------|---------|
| **社群** | 每月有互動（反應、留言、收藏）的人數比例；每篇好友看得到的食譜平均收到的反應與收藏；朋友的食譜被收藏、被「記錄我做的版本」的次數；每人平均好友數 | 朋友是不是彼此的靈感來源 | 資料表 |
| **記錄** | 每月有記錄的人數比例；草稿變成正式發佈的比例；開始記錄後完成發佈的比例；有寫做法的比例；用說的比例；**AI 填好的欄位被作者修改的比例**（整理得準不準）；從開始記錄到發佈花多久；平均照片數 | 記錄的體驗夠不夠好 | 資料表＋事件 |
| **靈感** | 對話：每月有和大廚對話的人數比例、每段對話的輪數、對話後有收藏或記錄的比例；點子漏斗：顯示 → 點開 → 收藏 → 做了並記錄；各槽位（熟悉的／變化版／新挑戰）的採用率；「不想要」的原因分布；首頁大廚點子「留白」的比例 | 大廚的點子準不準、有沒有讓人想煮 | 事件 |
| **留存** | 註冊後第 1、2、3 個月還有打開的比例；**隔一個月以上才回來的人**，回來後當月有沒有交流 | 偶爾用的人是否仍覺得有價值 | 事件 |
| **新手引導** | 每一步的完成、跳過、流失比例；口味探索平均回答幾題；新手引導後首頁點子有出現的比例 | 哪一步讓人卡住 | 事件（見 [12 衡量方式](12-onboarding.md)） |
| **食材與廚具** | 每月有更新食材的人數比例；用哪種方式新增（快速新增、搜尋、盤點）；設定期限的比例 | 食材清單值不值得維護 | 資料表＋事件 |
| **穩定度** | 照片上傳失敗率、AI 被擋下或出錯的次數、權限錯誤 | 哪裡讓人挫折 | 事件＋AI 用量紀錄 |
| **成本** | 每人每月 AI 成本、照片儲存量 | 營運是否健康 | AI 用量紀錄、Storage |

前三個月先累積基準值，之後再設目標；不在上線前先訂數字。

### 功能使用率

每個功能算「**本月有打開 App 的人當中，用過至少一次的比例**」，並分成兩個數字來看：

| 數字 | 意思 | 低的時候要改什麼 |
|------|------|----------------|
| **到達率**：進到這個畫面或入口的人數比例 | 有沒有被發現 | 入口位置、導覽、首頁的提示 |
| **完成率**：進到畫面後完成主要動作的比例 | 用了喜不喜歡、順不順 | 功能本身的流程與介面 |

## 三、資料從哪裡來

### 1. 現有資料表（不用另外記錄）

資料都在雲端，食譜、收藏、反應、留言、好友關係、廚房本來就存在 Postgres（對話內容不納入統計）。主指標、社群與記錄的大部分指標，用 SQL 匯總就能算出來。

### 2. 產品事件（記錄操作過程）

資料表只看得到結果，看不到過程，例如「開了記錄畫面卻沒有發佈」。事件格式見 [05 ProductEvent](05-data-model.md#衍生快取資料由程式算出或後端產生)。

**事件清單**（名稱用「區域.動作」；屬性只能是白名單內的值，不能是自由文字）：

| 區域 | 事件 | 屬性 |
|------|------|------|
| App | `app.open`（回到前景；30 分鐘內算同一次）、`screen.view` | `screen`；`installed`（是否加到主畫面）、`platform` |
| 記錄 | `record.start`、`record.dictation_used`、`record.ai_filled`、`record.publish`、`record.abandon`、`record.draft_saved`、`record.draft_published`、`recipe.cook_again`、`recipe.refine_by_voice` | `entry`（＋記錄、烹飪模式、收藏、點子、又做了一次）；`photoCount`、`hasSteps`、`visibility`、`highlightCount`；`fieldsEditedAfterAi`（作者改了哪幾類 AI 填的欄位，只記類別，不記內容）；放棄時的 `step` |
| 食譜 | `recipe.cooking_mode_start`、`recipe.cooking_mode_finish`、`recipe.shopping_list_shared`、`recipe.import` | `importType`（網址） |
| 靈感 | `chat.start`、`chat.message_sent`、`chat.ingredients_added`、`suggestion.shown`、`suggestion.opened`、`suggestion.bookmarked`、`suggestion.recorded`、`suggestion.dismissed` | `turn`、`count`、`source`（首頁、對話）、`slot`、`dismissReason`；**不記對話內容** |
| 食材 | `pantry.add`、`pantry.remove`、`pantry.restore`、`pantry.expiry_set`、`pantry.stocktake` | `method`（快速新增、搜尋、盤點）、`count` |
| 社群 | `friend.added`、`feed.end_reached`、`social.reaction`、`social.comment`、`social.bookmark`、`social.version_recorded`、`social.share_to_friend` | `via`（好友連結、QR Code、邀請） |
| 分享 | `share.link_created`、`share.text_copied`、`share.card_saved` | — |
| 新手引導 | `onboarding.step`、`taste.answered` | `step`、`action`（開始、完成、跳過）；`questionType` |
| 設定 | `settings.changed` | `key`（例：單位、大廚模式、預設可見範圍） |
| 錯誤 | `error` | `kind`（照片上傳、AI 被擋下、權限、網路） |
| 微問卷 | `survey.answered` | `question`、`answer`（👍／👎） |

- 前端送事件時批次送出（例：每 10 秒或離開畫面時），不影響操作速度；送不出去就丟掉，不重試、不暫存。
- 原始事件保留 **13 個月**，每月匯總成統計表後，舊的原始事件刪除；匯總結果長期保留。
- 事件裡存的是每人一組隨機的**分析 ID**，不是使用者 ID；對照表只有後端的匯總排程讀得到，刪除帳號時刪掉對照，留下的事件就無法對回這個人。
- 新增事件要更新這份清單與隱私說明，不能在程式裡隨意加。

### 3. 直接問人（質性）

| 方式 | 頻率 | 說明 |
|------|------|------|
| 回饋收件匣 | 隨時 | App 內「回報問題／給建議」（02 L 節，M2） |
| 訪談 | 每季 3–5 人、每人 20 分鐘 | 特別找**很久沒打開的人**和**新加入的人**；問「上次打開是為了什麼」「哪裡卡住」 |
| 微問卷 | 每人每月最多一題 | 在完成某件事之後輕輕問一句，例如記錄完問「這次記錄順手嗎？👍👎」。可以直接關掉；關閉「使用統計」的人不會出現 |
| 「不想要」的原因 | 隨時 | 已在點子回饋中收集 |

## 四、在哪裡看

### 後台的「產品數據」模組（M2）

| 區塊 | 內容 |
|------|------|
| 主指標 | 每月有料理交流的人數比例，最近 12 個月的趨勢 |
| 輔助指標 | 社群、記錄、靈感、留存、食材、穩定度、成本，各一張月趨勢 |
| 漏斗 | 點子漏斗、記錄流程（開始 → 選照片 → 發佈）、新手引導每一步 |
| 功能使用率 | 每個功能的到達率與完成率排行，標出「沒被發現」和「用了但沒完成」 |
| 留存 | 依註冊月份分組的回訪表（以月為單位） |
| 微問卷與「不想要」 | 每題的 👍／👎 比例、「不想要」的原因分布 |

- 一律只顯示匯總；分組少於 5 人時顯示「人數太少」。
- 不提供查詢單一使用者事件的功能。AI 用量的「每位使用者用量排行」只用於成本與用量保護，不放行為資料。

### 自己深入分析

想自己做交叉分析時，用一個**唯讀資料庫帳號**連接免費的報表工具（例：Metabase）。這個帳號只能讀「匯總後的統計表」與事件（不含 `userId`），讀不到食譜、留言等內容表。

### 檢視節奏

- **每月**：看一次產品數據，挑一到兩個最明顯的問題（流失最多的一步、使用率最低的功能）。
- **每季**：做一輪訪談，確認數字背後的原因，決定下一季要改的地方。
- **改版前後比較**：改一個流程後，比較前後各一個月的完成率。人數少，**不做 A/B 測試**；開放註冊、人數上來之後再考慮。

## 五、刻意不做的

| 不做 | 原因 |
|------|------|
| 第三方分析工具（Google Analytics、Mixpanel 等） | 資料會送到別的公司 |
| 錄下操作畫面（session replay）、熱點圖 | 看得到太多私人內容，違反「看不到別人的生活」 |
| 每日活躍、連續天數當目標 | 違反「偶爾用也完整」，會把產品優化成催促使用者 |
| 對使用者顯示任何使用統計 | 產品原則：不顯示頻率與次數 |
| 用行為資料做個人化以外的用途 | 事件只用於改善產品；個人化推薦用的是口味地圖與回饋（[13](13-taste-preferences.md)） |

## 六、上線時程

| 階段 | 內容 |
|------|------|
| M0 | 只有你自己使用，不記錄事件；直接用體感驗收 |
| M1a | 事件記錄開始（和邀請朋友同時）：App、記錄、靈感、新手引導、錯誤；隱私說明（口頭）告知記錄範圍；設定加上「不參與使用統計」 |
| M2 | 補上社群、分享、食材的事件；後台「產品數據」模組；微問卷；第一次季訪談 |
| M3 之後 | 依需要增加事件；唯讀帳號接報表工具 |

## 七、之後可以擴充與檢討

上線後依實際使用再看的事。類型：**擴充**＝之後可以加的功能；**優化**＝讓現有的更好；**檢討**＝回頭確認當初的決定還對不對。全部項目依時間整理在 [08 第四部分](08-open-items.md#四之後可以擴充優化或檢討)。

| 項目 | 類型 | 什麼時候看 | 怎麼判斷 |
|------|------|-----------|---------|
| 和大廚對話的使用率 | 檢討 | M1a 上線兩個月後 | 對話是首頁的核心假設：每月有對話的人少於三成時，檢討首頁的位置與大廚區塊的設計 |
| 對話後有沒有煮 | 擴充 | M2 後 | 加上「對話後一週內記錄了相關的菜」的比例，判斷對話是否真的讓人想煮 |
| 「用說的」的使用率與修改率 | 檢討 | 「用說的」上線一個月後 | 用說的比例低，檢討入口；AI 填的欄位修改率高，檢討整理的品質 |
| 從開始記錄到發佈的時間 | 檢討 | 「用說的」上線一個月後 | 目標是累的時候 30 秒內能發佈；比較用說的和自己打的差距 |
| 有做法的食譜比例 | 檢討 | 「用說的」上線三個月後 | 「用說的」要解決「朋友的拿手菜學不到」：有做法的比例沒有提高，就要重新想 |
| 難易度的調整率 | 檢討 | 難易度自動估上線三個月後 | 作者調整 AI 估的難易度的比例與方向 |
| 列出要買的勾選修改 | 檢討 | M1 後 | 使用者常改預先勾選的項目，代表 App 記的食材和實際差很多；看要不要改成不預先勾選 |
| 收藏變成「做過了」的比例 | 檢討 | M2 後 | 收藏很多、做過的很少時，檢討收藏提醒的設計 |
